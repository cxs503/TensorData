# Model asset registry v1 (`model-manifest/1.0`)

A **model asset** here is not a weights file. It is a six-part contract: *what task*, *what
input/output convention*, *which weights bytes*, *which training data*, *how well it did on data
it never saw*, and *where the numbers may be trusted*. The registry stores all six in one
immutable, content-addressed record, so a downstream solver job can consume a surrogate by
identity instead of by path.

Motivation (2026-11-13 asset-form survey): model weights were the one asset form with no
structure — see [inventory](../artifacts/GAP-ASSET-MODEL-REGISTRY/inventory.md) (generated by
`scripts/model_asset_inventory.py`): **306 loose weight-like files** on this platform, of which
only **6 are model-asset candidates** (a `models/` directory or an experiment bundle); the rest
are tensor dumps and benchmark caches. Before this mission exactly one of those candidates had a
declared task, an eval card and a data fingerprint: none.

## 1. Manifest schema

JSON Schema: [`schemas/model-manifest.schema.json`](../../schemas/model-manifest.schema.json)
(draft 2020-12). Structural validation is mirrored in
[`tensordata/modelreg/schema.py`](../../tensordata/modelreg/schema.py) so the registry works
without `jsonschema` installed; the two are kept intentionally in step.

| block | required content | why it is not optional |
|---|---|---|
| `model_id`, `version` | lowercase slug + semver; `(model_id, version)` is immutable | a path is not an identity; a version cannot be re-pointed |
| `task` | `task_type`, `objective`, `targets[]` (name/unit/condition) | a frozen random tensor and a surrogate are indistinguishable without a declared task |
| `io_contract` | `inputs[]`/`outputs[]` (name, media_type, shape, dtype, units, columns), `batch_axis`, `preprocessing`, `loader` | column order and scaling are the #1 silent-mismatch source; they are declared, never guessed by the loader |
| `artifacts[]` | `role`, registry-relative `path`, `sha256`, `bytes`, `format`, `framework` | digests are recomputed from the files; a client cannot assert its own hash |
| `training_data` | `datasets[]` (ref, version, source, fingerprint), composite `fingerprint`, `fingerprint_recipe`, `split` | binds the weights to *this* table and *this* train/test membership (张冠李戴 defence) |
| `evaluation` | `protocol`, `metrics` (per target), `status`, optional `baseline` | a metric without "held out what, scored how" is not evidence |
| `applicability_domain` | `description`, componentwise `bounds`, `out_of_domain_policy` (`flag`/`reject`), `caveats` | a surrogate outside its training box is an extrapolation, and callers must be able to see that |
| `provenance` | `created_by`, `repro_cmd`, optional `code`/`inputs` | one command must retrain the asset |
| `rights` | `license`, `data_license` | weights inherit the training data's licence obligations |

`manifest_sha256` is the sha256 of the canonical (sorted-key, whitespace-free) manifest body
without that field — the same construction the dataset manifests already use.

### Fingerprints: what exactly is hashed

`training_data.fingerprint` is `sha256:` over canonical JSON of
`{array digest for each array} ∪ {extra binding material}` where

* an *array digest* = sha256 over `dtype|shape|` + the C-order bytes of the array,
* *extra* = the mat/table source sha256, target column names, seed and dtypes.

The recipe is stored in the manifest (`fingerprint_recipe`), so `verify` can recompute it from the
registered `training_table.npz` alone. Two tables with identical numbers but different train/test
membership cannot collide, because the split index arrays are part of the fingerprint.

## 2. Registry layout and invariants

```
models/<model_id>/<version>/
  model.json              # canonical manifest (manifest_sha256 inside)
  weights/model.pt        # declared payload(s): weights, tokenizer, ...
  eval_card.json          # full evaluation evidence (metrics, baseline, split, env)
  training_table.npz      # fingerprint source (optional but required by verify for binding)
```

* **Immutable versions.** Re-registering `(model_id, version)` raises `RegistryError`;
  changing any byte means a new version.
* **Server-side hashing.** `registry.register(manifest, {rel_path: source_file})` recomputes
  sha256 and size for every supplied payload and writes them into the manifest, then validates,
  then publishes by atomic directory rename — a half-written model is never listed.
* **Self-checksummed.** `manifest_sha256` covers every other manifest field, so editing the
  declared applicability domain, metrics or artifact list is detectable.
* **Verify is a re-derivation, not a flag.** `registry.verify()` re-reads the manifest, re-hashes
  every artifact, and re-computes the training-table fingerprint. It reports one check per
  artifact plus `training_data_fingerprint`, and fails if anything disagrees. The only
  non-failing "unknown" state is when the training table is not shipped with the model
  (`status: unchecked`) — that is reported explicitly, not hidden.

## 3. Load-and-use

```python
from tensordata.modelreg import ModelRegistry, load_model

reg = ModelRegistry("models")                       # or TENSORDATA_MODEL_REGISTRY_ROOT
reg.list_models()                                   # catalogue rows
reg.verify("dtmb5415-lumped-surrogate")             # recompute hashes + data fingerprint
model = load_model(reg, "dtmb5415-lumped-surrogate")
X = [[0.0] * 27, [0.5] * 27]                        # (n, 27) design vectors
out = model.predict(X)                              # (2, 9) responses
report = model.predict_report(X)                    # + applicability-domain flags
```

CLI (same registry, no server needed):

```bash
python -m tensordata.modelreg.cli list --json
python -m tensordata.modelreg.cli show dtmb5415-lumped-surrogate
python -m tensordata.modelreg.cli verify dtmb5415-lumped-surrogate@1.0.0   # exit 1 on mismatch
python -m tensordata.modelreg.cli predict dtmb5415-lumped-surrogate --input rows.json --out out.json
python -m tensordata.modelreg.cli fingerprint --table training_table.npz
python -m tensordata.modelreg.cli inventory --scan /root/tensor-ecosystem --out inv.json
```

HTTP (API key required, like every data route):

| method | path | purpose |
|---|---|---|
| `GET` | `/api/v1/models` | catalogue |
| `POST` | `/api/v1/models` | register: `manifest` form field + payload files whose **filename is the manifest-relative path**; digests recomputed server-side |
| `GET` | `/api/v1/models/{model_id}` | manifest (latest or `?version=`) |
| `GET` | `/api/v1/models/{model_id}/versions` | version list |
| `GET` | `/api/v1/models/{model_id}/verify` | 200 when consistent, **409** with the check table when not |
| `POST` | `/api/v1/models/{model_id}/predict` | `{"inputs": [[...]], "version": optional}` → outputs + domain flags |

### Loader kinds

* `numpy-affine` — `weights.npz` with `W`, `b` (linear/ridge baselines, tests; numpy only).
* `torch-mlp` — `weights/model.pt` holding a `state_dict`, layer widths declared in
  `io_contract.loader.layers`; torch is imported lazily, so registration/inventory/verify work on
  installations without torch.

Pre/post-processing (`input_center/scale`, `output_center/scale`) lives in the manifest and is
applied by the loader — the checkpoint is not trusted to carry its own convention.

## 4. Applicability domain

`applicability_domain.bounds` is keyed by the declared input name and applied componentwise
(e.g. `{"design_variables": [-1.03, 1.03]}`). `predict_report()` returns
`out_of_domain.n_out_of_domain` and the offending row indices; `policy: "reject"` turns the
flag into a `LoaderError`. Bounds are **data-derived** (the training table's actual min/max,
rounded outward), not aspirational.

## 5. Inventory of pre-existing model files

`scripts/model_asset_inventory.py` walks scan roots for weight-like suffixes, records sha256,
size, git repo, tracked/untracked state, and reconciles each sha256 against every registered
artifact — a byte-identical copy elsewhere on disk is linked to its model identity instead of
being a mystery file. Path *hints* (`model_dir`, `experiment_bundle`, `benchmark_cache`,
`artifact_dump`, `unknown`) are triage only; the sha256 reconciliation is the authoritative link.

Result on 2026-11-13 (see `artifacts/GAP-ASSET-MODEL-REGISTRY/inventory.{json,md}`): 308
weight-suffixed files, 6 model-asset candidates, 109 tensor dumps/caches, 304 unregistered.
The honest reading: the platform has **lots of `.pt` tensors and almost no declared models** —
which is exactly the gap this registry closes (first registered asset:
[`dtmb5415-lumped-surrogate`](dtmb5415-lumped-surrogate.md)).

## 6. Limitations / not claimed

* No database table: the registry is an immutable file tree (same philosophy as dataset
  manifests). There is no cross-registry query language, no access control beyond the API key,
  and no garbage collection of superseded versions.
* `verify` cannot re-derive the fingerprint if a model ships without its `training_table.npz`;
  it says `unchecked` rather than passing silently.
* Only two loader kinds are implemented. A model whose framework is not covered can be
  registered and verified, but not loaded.
* Model *card* documents are generated (`scripts/render_model_card.py`) but not yet gated in CI;
  a metric edited in the manifest would not fail a test today.
* Rights approval is recorded, not enforced: nothing stops registering a model whose data
  licence forbids redistribution.
